# `ue settings`

UETools preserves explicitly selected `.code-workspace` customizations when Unreal regenerates project files. It preserves additions, modifications, and intentional removals without treating every old workspace value as user-owned.

This solves the problems caused by the previous missing-property merge:

- A deliberately removed Unreal-generated value stays removed.
- A custom value survives regeneration only after it is explicitly captured or adopted.
- A field that Unreal stops generating is allowed to disappear when it is not owned.
- A new field introduced by Unreal survives when no overlay owns it.
- An Unreal change to an owned value stops as a conflict instead of silently choosing one side.
- The full Engine directory can be removed from `folders` through portable team intent rather than a machine-specific absolute path.

UETools manages repository workspace files only. It does not change VS Code user profiles, installed extensions, Settings Sync, accounts, or editor UI state.

## Mental model

The system keeps two snapshots in an ignored provenance ledger:

1. **Pristine**: the last workspace generated by Unreal before overlays.
2. **Effective**: the workspace after Team, User, and Project operations were applied.

On the next synchronization, UETools compares owned non-removal values in the old pristine workspace with the new pristine workspace. If Unreal did not change an owned target, UETools reapplies the operation. Removal tombstones are reapplied whenever their target returns.

```text
last pristine Unreal workspace ── compare owned targets ── new pristine Unreal workspace
                                                              +
                                      Team -> User -> Project overlay operations
                                                              |
                                                              v
                                                   new effective workspace
                                                              +
                                                   updated provenance ledger
```

Unknown differences are never promoted to ownership by `settings sync`. Use `settings capture` for edits made after the ledger exists, or `settings adopt` for customization that predates the ledger.

## Before running a command

Run commands from the Unreal project repository, or pass `-RepoRoot`. When a repository contains multiple workspace files, always pass `-WorkspacePath`.

Relative workspace paths are resolved against the selected repository root, not against an arbitrary caller directory:

```powershell
ue settings status -WorkspacePath ".\CPP_Tests.code-workspace"
ue settings sync -WorkspacePath ".\CPP_Tests.code-workspace" -DryRun
```

Both launchers use the same command domain:

```powershell
ue settings help
ue-tools settings help
```

If you are testing a change from the UEToolSuiteInstaller source repository, update/install that revision into the target Unreal repository first. The stable `ue` command runs the installed global runtime, not the source file merely because it was edited in the installer checkout.

## First-run decision

Start with:

```powershell
ue settings status -WorkspacePath ".\CPP_Tests.code-workspace"
```

Then choose one path:

### Existing workspace already contains customization

Use adoption. Adoption snapshots the current workspace, regenerates a pristine Unreal workspace, compares the two, and lets you classify selected differences.

```powershell
# Describes the operation without regenerating or writing files.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace" `
  -Scope User -Path /settings -DryRun -NonInteractive

# Interactive adoption: prompts for scope and candidate changes.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace"

# Explicit automation-friendly adoption.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace" `
  -Scope User -Path /settings -Path /extensions/recommendations -NonInteractive
```

The dry run intentionally does not regenerate, so it describes the requested adoption but cannot enumerate the actual pristine-versus-custom candidate list. A real adoption restores the original workspace if regeneration, comparison, validation, or writing fails.

### Workspace is known to be pristine

A normal regeneration-enabled build can initialize provenance automatically when the pre-regeneration and post-regeneration workspaces are semantically identical:

```powershell
ue build -NoBuild -WorkspacePath ".\CPP_Tests.code-workspace" -NonInteractive
```

If they differ, UETools restores the original workspace and requires adoption. It does not guess which differences are custom.

### A ledger already exists

Use `status`, `sync`, and `capture`. `settings adopt` refuses to run while a ledger exists because it is only a first-time or ledger-rebuild workflow.

## Command reference

### `settings sync`

Apply operations that are already owned. This command never captures the current workspace.

```powershell
ue settings sync
ue settings sync -WorkspacePath ".\CPP_Tests.code-workspace"
ue settings sync -WorkspacePath ".\CPP_Tests.code-workspace" -DryRun
ue settings sync -RepoRoot "C:\Projects\CPP" `
  -WorkspacePath ".\CPP_Tests.code-workspace" -NonInteractive
```

With suite hooks enabled, pulling or checking out a commit that creates, changes, deletes, or renames the Team overlay automatically runs the same settings planner. Use the explicit command when hooks are disabled, after manually regenerating project files outside UETools, to preview with `-DryRun`, or whenever the live workspace has drifted from the last effective state.

`-DryRun` uses the same planner as apply mode. It validates the workspace, overlays, state, semantic selectors, and conflicts, but writes no workspace, overlay, selection, state, or backup file.

Sync requires an existing ledger. If none exists, use adoption or a normal regeneration-enabled build.

### `settings capture`

Compare the live workspace with the last effective snapshot and turn selected differences into owned operations.

```powershell
# Share a scalar setting with the team.
ue settings capture -Scope Team `
  -Path /settings/editor.formatOnSave -NonInteractive

# Reuse extension recommendations across this user's projects.
ue settings capture -Scope User `
  -Path /extensions/recommendations -NonInteractive

# Keep project-specific tasks private.
ue settings capture -Scope Project `
  -Path /tasks/tasks -NonInteractive

# Capture several non-overlapping paths by repeating -Path.
ue settings capture -Scope Project `
  -Path /settings/editor.fontSize `
  -Path /settings/files.exclude `
  -DryRun -NonInteractive

# Omit -Path to scan the whole workspace and select changes interactively.
ue settings capture -Scope User
```

Capture recognizes:

- additions that are present only in the live workspace;
- modifications whose live value differs from the last effective value;
- property removals whose previous effective value is now absent;
- string-array additions and removals;
- keyed-array additions, changes, and removals by stable identity;
- removal of the active Engine workspace folder as a portable semantic operation.

`-Scope` is required. In noninteractive mode, at least one explicit `-Path` is required. Repeat `-Path` for multiple JSON Pointers; do not place several pointer values after a single `-Path` token.

Use non-overlapping paths. For example, do not capture both `/settings` and `/settings/editor.fontSize` in the same command because the broader path already contains the narrower change.

### `settings adopt`

Create the first ledger for a workspace that may already contain custom content.

```powershell
# Full interactive review.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace"

# Adopt selected paths into a private reusable profile.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace" `
  -Scope User -Path /settings -Path /extensions/recommendations -NonInteractive

# Describe a planned adoption without regeneration or writes.
ue settings adopt -WorkspacePath ".\CPP_Tests.code-workspace" `
  -Scope Project -Path /tasks/tasks -DryRun -NonInteractive
```

A real adoption performs these steps:

1. Save the original workspace bytes.
2. Run the existing Unreal regeneration workflow with build and settings sync disabled.
3. Treat the regenerated file as pristine Unreal output.
4. Compare the old workspace against pristine output.
5. Present candidate additions, modifications, and removals in interactive mode.
6. Store only the selected operations in the chosen scope.
7. Apply all layers and atomically write the overlay, effective workspace, and ledger.
8. Restore the original workspace if any step fails.

Noninteractive adoption requires both `-Scope` and at least one `-Path`.

### `settings status`

Show the selected workspace, active user profile, state location, overlay paths, operation counts, individual owned operations, live drift, and detected conflicts.

```powershell
ue settings status
ue settings status -WorkspacePath ".\CPP_Tests.code-workspace"
ue settings status -RepoRoot "C:\Projects\CPP" `
  -WorkspacePath ".\CPP_Tests.code-workspace"
```

Status does not write files. It does not accept `-DryRun`, `-NonInteractive`, `-Scope`, or `-Path` because those options do not apply to inspection.

### CLI help pages

The settings overview lists every command, first-run guidance, and all supported help forms:

```powershell
ue help settings
ue settings help
```

Every command has a detailed page containing its purpose, behavior, accepted options, examples, prerequisites, and safety notes. These three forms are equivalent:

```powershell
ue help settings sync
ue settings help sync
ue settings sync help
```

Replace `sync` with `capture`, `adopt`, or `status` for the other pages:

```powershell
ue help settings capture
ue help settings adopt
ue help settings status

ue settings capture help
ue settings adopt help
ue settings status help
```

The long-form `ue-tools` launcher exposes the same pages. For example, `ue-tools help settings sync` and `ue-tools settings sync help` are equivalent to the commands above.

Options are validated per subcommand. An option intended for another command now produces command-specific guidance rather than a PowerShell parameter-binding error.

## Option matrix

| Option | sync | capture | adopt | status | Meaning |
|---|---:|---:|---:|---:|---|
| `-RepoRoot <path>` | yes | yes | yes | yes | Select the Unreal repository explicitly. |
| `-WorkspacePath <path>` | yes | yes | yes | yes | Select a `.code-workspace`; relative paths resolve from `RepoRoot`. |
| `-DryRun` | yes | yes | yes | no | Validate/preview without writes. Adoption also skips regeneration. |
| `-NonInteractive` | yes | yes | yes | no | Disable prompts; capture/adopt then require explicit paths. |
| `-Scope Team|User|Project` | no | required | optional interactively, required noninteractively | no | Choose the overlay that will own captured/adopted operations. |
| `-Path <json-pointer>` | no | optional interactively, required noninteractively | optional interactively, required noninteractively | no | Select a structural workspace path; repeat for multiple paths. |

## JSON Pointer paths

Paths use JSON Pointer syntax, not PowerShell property syntax:

```text
/settings/editor.formatOnSave
/settings/files.exclude
/extensions/recommendations
/folders
/tasks/tasks
/launch/configurations
/launch/compounds
/inputs
```

Rules:

- A path starts with `/`.
- A literal `/` inside a property name is escaped as `~1`.
- A literal `~` inside a property name is escaped as `~0`.
- Dots have no special meaning. `editor.formatOnSave` is one literal key.
- Invalid `~` escapes are rejected.
- The empty pointer means the whole workspace and is used by interactive capture/adoption.
- Capture a known array at its container path, such as `/tasks/tasks`, rather than by numeric element index.

Unknown object-array shapes are rejected because UETools cannot safely identify entries. They require an explicit identity strategy in a manually reviewed overlay.

## Storage, tracking, and precedence

Layers apply from lowest to highest precedence:

| Order | Scope | Location | Git/privacy behavior |
|---:|---|---|---|
| 1 | Team | `<RepoRoot>\.ue-tools\workspace-settings\team.jsonc` | Portable and intentionally tracked. |
| 2 | User | `%LOCALAPPDATA%\UEToolSuite\workspace-settings\profiles\<profile-id>.jsonc` | Private, machine-local, reusable across projects. |
| 3 | Project | `<RepoRoot>\.ue-tools\local\workspace-settings.jsonc` | Private to this user/project and ignored. |
| - | Profile selection | `<RepoRoot>\.ue-tools\local\workspace-profile.json` | Private and ignored. |
| - | Provenance state | `<RepoRoot>\.ue-tools\state\workspace-sync\<workspace-id>.json` | Runtime state and ignored. |

The default user profile is always `default`; it is not derived from a username. To select another profile, create the ignored selection file:

```json
{
  "profileId": "workstation"
}
```

Profile IDs may contain letters, numbers, dots, underscores, and hyphens and are limited to 64 characters.

Team overlays reject absolute paths, URLs/private hosts, credential-like fields, tokens, account state, and other machine-specific values. Put those values in User or Project scope. Portable semantic selectors are allowed in Team scope.

## Overlay schema and operations

All overlays use schema version 1:

```jsonc
{
  "schemaVersion": 1,
  "scope": "Team",
  "operations": [
    {
      "op": "set",
      "path": "/settings/editor.formatOnSave",
      "value": true
    },
    {
      "op": "removeSemantic",
      "path": "/folders",
      "selector": "activeUnrealEngineRoot"
    }
  ]
}
```

| Operation | Purpose |
|---|---|
| `set` | Add or replace one scalar or object leaf. |
| `mergeObject` | Recursively expand an object into separately owned leaf operations. |
| `removeProperty` | Keep a JSON property absent. |
| `addStringItem` | Keep one string present in a string array. |
| `removeStringItem` | Keep one string absent from a string array. |
| `upsertKeyedItem` | Add or update one object-array item by identity. |
| `removeKeyedItem` | Keep one identified object-array item absent. |
| `removeSemantic` | Remove an item identified from portable runtime/project meaning. |

Known object-array identities are:

| Array path | Identity |
|---|---|
| `/folders` | normalized `path` |
| `/tasks/tasks` | `label` |
| `/launch/configurations` | `name` |
| `/launch/compounds` | `name` |
| `/inputs` | `id` |

Object ownership is leaf-grained. Owning `/settings/files.exclude/Build` does not own the whole `/settings` object. Duplicate, contradictory, overlapping, ambiguous, and identity-colliding operations fail before a write.

## Portable Engine-folder removal

Unreal may regenerate an absolute Engine source entry in `folders`. Opening that directory as a workspace root increases watching, search, Git discovery, extension activation, and indexing, while C++ include resolution remains available through Unreal's compile commands and response files.

To remove it for the team:

1. Open the selected `.code-workspace` file.
2. Remove only the folder entry whose path points to the active Unreal Engine root or its `Engine` child.
3. Save the workspace.
4. Preview capture:

   ```powershell
   ue settings capture -Scope Team -Path /folders `
     -WorkspacePath ".\CPP_Tests.code-workspace" -DryRun -NonInteractive
   ```

5. Confirm the output contains `removeSemantic /folders`.
6. Apply capture without `-DryRun`.
7. Review `.ue-tools\workspace-settings\team.jsonc` and confirm it contains `activeUnrealEngineRoot`, not your absolute Engine path.
8. Commit only the reviewed Team overlay with the rest of the intended change.

During sync, the selector uses the existing project-context Engine resolver. It resolves relative or absolute folder paths, normalizes Windows separators, case, and trailing separators, and removes exactly one match. Zero matches is a harmless tombstone no-op. More than one match is an ambiguity error and nothing is written.

Each teammate resolves their own Engine installation, so paths may differ across drives and Epic installations.

## Common workflows

### Share a setting through Git

1. Edit the workspace.
2. Run `ue settings capture -Scope Team -Path <pointer> -DryRun -NonInteractive`.
3. Review the reported operation.
4. Run the same command without `-DryRun`.
5. Review and commit `.ue-tools\workspace-settings\team.jsonc`.
6. Teammates pull or check out the commit. Enabled suite hooks apply the Team overlay automatically; `ue settings sync` remains the fallback when hooks are disabled or a manual preview is needed.

### Reuse a personal setting across projects

1. Edit the workspace.
2. Capture to `User`.
3. Confirm `settings status` reports the active profile.
4. Other projects selecting the same profile apply those operations during their own sync.

The user overlay may contain machine-specific paths and must not be copied into Git.

### Keep a setting private to one project

1. Edit the workspace.
2. Capture to `Project`.
3. Verify `.ue-tools\local\workspace-settings.jsonc` is ignored.
4. Run sync after future manual regenerations.

### Stop owning a path or remove a tombstone

1. Find the operation with `ue settings status`.
2. Remove that operation from its overlay.
3. Run `ue settings sync -DryRun`.
4. Confirm the result, then run sync without `-DryRun`.

The effective workspace returns to the pristine Unreal value when no higher-precedence operation owns that target.

### Move ownership between scopes

1. Copy or recapture the intended operation into the destination scope.
2. Remove the old operation from the source overlay.
3. Validate with `settings sync -DryRun`.
4. Apply sync and inspect status.

Do not leave contradictory add/remove intent split between scopes.

## Build and regeneration integration

`ue build` and hook-driven Unreal synchronization use the same planner as `ue settings sync`:

1. Validate overlays and ledger before cleanup or regeneration.
2. Snapshot the effective workspace and `.ignore`.
3. Regenerate project files when requested.
4. Treat Unreal's output as the new pristine workspace.
5. Compare old/new pristine values at owned non-removal targets.
6. Apply Team, User, and Project operations.
7. Atomically write the effective workspace and ledger.
8. Continue to build only after settings reconciliation succeeds.

On conflict or failure, the pre-operation workspace and `.ignore` are restored and the build stops.

### Automatic Team-overlay synchronization from Git hooks

The installed `post-merge` and branch `post-checkout` flows already pass the old and new Git revisions into UETools. The action planner treats this tracked path as a dedicated settings trigger:

```text
.ue-tools/workspace-settings/team.jsonc
```

Creation, modification, deletion, and rename to or from that path trigger automatic reconciliation. An overlay-only change:

1. Runs without an interactive prompt.
2. Validates the Team, User, and Project layers and the local ledger.
3. Applies the settings planner atomically.
4. Updates only the ignored workspace and provenance ledger when needed.
5. Does not clean generated directories, regenerate project files, or build the Editor.

If the same revision range also contains Unreal build or regeneration triggers, the normal Unreal workflow performs settings reconciliation at its existing safe boundary.

A settings conflict or invalid overlay stops reconciliation before writes. The Git merge or checkout remains completed, the hook reports the failure and `ue settings status` recovery command, and the developer resolves the workspace issue locally. Hooks never adopt unknown customization. A machine without a ledger must still use first-run regeneration for a known-pristine workspace or `settings adopt` for an already-customized workspace.

`-NoRegen` still synchronizes settings:

```powershell
ue build -NoRegen -NoBuild -WorkspacePath ".\CPP_Tests.code-workspace"
```

Use `-SkipSettingsSync` only for an intentional diagnostic or for adoption's controlled pristine regeneration:

```powershell
ue build -NoRegen -NoBuild -SkipSettingsSync
```

## Conflicts and recovery

An owned non-removal operation uses strict three-way comparison. If Unreal changes the generated value or begins generating a previously custom-only identity, sync reports:

- JSON path;
- previous Unreal value;
- new Unreal value;
- owning layer;
- custom operation;
- resolution guidance.

Nothing is written when any conflict exists. A removal tombstone reappearing is expected and is removed again; it is not a conflict.

To resolve a conflict:

1. Run `ue settings status` or `ue settings sync -DryRun`.
2. Decide whether Unreal's new value or the custom operation should win.
3. Remove or update the owning operation. If the live workspace now expresses the desired value, use `settings capture` on the narrow path.
4. Run dry-run again.
5. Apply only after conflicts are zero.

### Malformed or stale ledger

Malformed and stale state now fails with the ledger path and the mismatched field. Preserve the overlays, move the bad state file or `workspace-sync` directory aside as a recoverable backup, then run adoption. Do not delete Team/User/Project overlays when rebuilding state.

### Rebuild the ledger

1. Back up `.ue-tools\state\workspace-sync`.
2. Preserve all overlay files.
3. Move the affected ledger out of the state directory.
4. Run `settings adopt` if the live workspace may contain customization.
5. Use regeneration initialization only when the workspace is known pristine.

## Troubleshooting

### `A parameter cannot be found that matches parameter name 'Path'`

This was caused by the settings parser forwarding a capture-only empty `Path` parameter into `sync`. The parser now emits only parameters valid for the selected subcommand. If the error remains, the target project is running an older installed global runtime; update UEToolSuite in that target repository and retry.

### `No workspace provenance ledger exists`

`settings sync` does not infer ownership or create a baseline from an unknown live workspace. Run adoption for a customized workspace, or let a regeneration-enabled build initialize a workspace known to be pristine.

### `Workspace path does not exist`

The value is resolved relative to `RepoRoot`. Check both explicitly:

```powershell
ue settings status -RepoRoot "C:\Projects\CPP" `
  -WorkspacePath ".\CPP_Tests.code-workspace"
```

### `A workspace provenance ledger already exists`

This is expected from `settings adopt` after the workspace already has a ledger. Adoption is only for first-time classification or an intentional ledger rebuild. Keep the ledger and use `settings capture` to record a newly edited live workspace.

### `No workspace changes were found relative to the last effective state`

The selected pointer has no semantic difference from the ledger's last effective snapshot. Check `settings status`, confirm the workspace was saved, and use the narrow path that actually changed.

When `-Path` is omitted, capture scans the whole workspace and presents every detected change interactively. This includes deletion of the active Engine entry from `folders`, even when other workspace arrays are empty. If an older installed runtime instead reports `No selected workspace changes were found`, update UEToolSuite in the target repository and retry. As an explicit diagnostic, run:

```powershell
ue settings capture -Scope Project -Path /folders `
  -WorkspacePath ".\CPP_Tests.code-workspace" -DryRun -NonInteractive
```

The preview should contain `Capture [Project]: removeSemantic /folders`. Remove `-DryRun` only after reviewing that output.

### Unknown or invalid option

Run command-specific help. `-Path` and `-Scope` apply only to capture/adopt; `status` accepts only repository and workspace selection options. Repeat `-Path` once per pointer.

### Team overlay rejects a value

Move personal paths, URLs/hosts, credentials, tokens, and account-specific values to User or Project scope. Do not weaken Team validation.

### Engine selector cannot resolve the Engine

Verify the `.uproject` Engine association or configured Engine root using the normal UETools/Unreal setup. The semantic selector intentionally fails closed when the active Engine cannot be resolved.

### Engine selector matched multiple folders

Remove duplicate Engine/Engine-source entries manually or replace the semantic operation with one carefully reviewed keyed operation. Sync does not guess which duplicate to remove.

### JSONC formatting changed

Comments are accepted while reading, but PowerShell has no native comment-preserving JSON syntax tree. When a semantic write is required, UETools may normalize JSON formatting and remove comments. A semantic no-op avoids rewriting the workspace or state.

## Manual verification checklist

Use a feature branch and a disposable or recoverable Unreal project workspace. Commit or back up the workspace before testing regeneration.

### 1. Confirm the installed command surface

- [ ] Update/install the current UEToolSuite revision into the target Unreal repository.
- [ ] Run `ue help settings` and confirm it lists `sync`, `capture`, `adopt`, and `status`.
- [ ] Run `ue help settings sync` and confirm it contains `What it does`, `Options`, and `Examples` sections.
- [ ] Run the equivalent `ue settings sync help` form and confirm the content matches.
- [ ] Repeat the detailed help check for `capture`, `adopt`, and `status`.
- [ ] Confirm the target workspace path resolves:

  ```powershell
  ue settings status -WorkspacePath ".\CPP_Tests.code-workspace"
  ```

- [ ] Confirm the old `parameter name 'Path'` error does not appear.

### 2. Establish provenance safely

- [ ] If status says state is missing and the workspace is customized, run an adoption dry run with explicit paths.
- [ ] Run real interactive or explicit adoption.
- [ ] If the workspace is known pristine instead, run a regeneration-only build and confirm automatic initialization succeeds.
- [ ] Run status again and confirm it prints a state path, all three layers, drift, and conflicts.

### 3. Verify sync and relative-path binding

- [ ] Run:

  ```powershell
  ue settings sync -WorkspacePath ".\CPP_Tests.code-workspace" -DryRun
  ```

- [ ] Confirm it lists the selected workspace and layers and reports no write.
- [ ] Run the same command without `-DryRun`.
- [ ] Confirm `ue settings status` reports `Drift: none` and `Conflicts: 0`.

### 4. Verify private scalar capture

- [ ] Add a temporary workspace setting such as `"uetools.manualCheck": true` under `settings`.
- [ ] Preview capture:

  ```powershell
  ue settings capture -Scope Project `
    -Path /settings/uetools.manualCheck `
    -WorkspacePath ".\CPP_Tests.code-workspace" `
    -DryRun -NonInteractive
  ```

- [ ] Confirm it reports an addition/set operation and writes nothing.
- [ ] Apply capture without `-DryRun`.
- [ ] Confirm `.ue-tools\local\workspace-settings.jsonc` owns only the selected leaf.
- [ ] Confirm `git status --short` does not show the private overlay or state.

### 5. Verify repeated paths

- [ ] Make two small, independent workspace edits.
- [ ] Capture them with two separate `-Path` options in one dry run.
- [ ] Confirm both paths appear independently and are not concatenated.

### 6. Verify portable Engine-folder removal

- [ ] Remove the active Engine folder entry from `folders` and save.
- [ ] Run interactive capture without `-Path`; confirm it lists `REMOVAL removeSemantic /folders`, select it, and keep `-DryRun` enabled for this pass.
- [ ] Preview Team capture for `/folders`.
- [ ] Confirm the operation is `removeSemantic` with selector `activeUnrealEngineRoot`.
- [ ] Apply capture.
- [ ] Inspect `.ue-tools\workspace-settings\team.jsonc` and confirm it contains no local drive or Engine installation path.
- [ ] Run regeneration without a build:

  ```powershell
  ue build -NoBuild -WorkspacePath ".\CPP_Tests.code-workspace" -NonInteractive
  ```

- [ ] Reopen the workspace JSON and confirm Unreal's regenerated Engine entry was removed again.
- [ ] Confirm the project folder remains in `folders`.

### 7. Verify future/unowned data behavior

- [ ] Add a temporary unowned top-level field in a disposable copy, run sync, and confirm sync does not claim it in an overlay.
- [ ] Regenerate through UETools and confirm new Unreal-generated unowned fields survive.
- [ ] Confirm obsolete unowned generated fields are not copied back from the old effective workspace.

### 8. Verify idempotence

- [ ] Record the workspace hash:

  ```powershell
  $before = (Get-FileHash -LiteralPath ".\CPP_Tests.code-workspace" -Algorithm SHA256).Hash
  ue settings sync -WorkspacePath ".\CPP_Tests.code-workspace" -NonInteractive
  $after = (Get-FileHash -LiteralPath ".\CPP_Tests.code-workspace" -Algorithm SHA256).Hash
  $before -eq $after
  ```

- [ ] Confirm the result is `True` when no semantic change is needed.
- [ ] Run status and confirm no drift or conflicts.

### 9. Verify tracking/privacy boundaries

- [ ] Confirm the Team overlay is visible to Git when changed.
- [ ] Confirm `.ue-tools\local\` is ignored.
- [ ] Confirm `.ue-tools\state\` is ignored.
- [ ] Confirm the LocalAppData User profile is outside the repository.
- [ ] Review the Team overlay for absolute paths, hosts, tokens, credentials, or account data before committing.

### 10. Verify automatic Team-overlay hook synchronization

- [ ] On a disposable branch or clone with suite hooks enabled, create or modify `.ue-tools\workspace-settings\team.jsonc` in one commit.
- [ ] Pull or check out that commit on a machine with an existing ledger.
- [ ] Confirm the hook reports `synchronize VS Code workspace settings` and lists the Team overlay path.
